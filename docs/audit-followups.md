# Audit Follow-ups

Items from the codebase audit that were NOT addressed in the initial pass —
either deferred by design, blocked on a real environment, or future work that
should land before going to production traffic.

## Future work — must land before production scale

### Implement `VercelBlobStorage` (was P0.1)

Currently `lib/staging/index.ts` throws a clear error if `STAGING_DRIVER=blob`
would be selected. This is a fail-fast stopgap so a misconfigured Vercel deploy
fails immediately instead of crashing mid-pipeline. It is **not** a real
solution — the moment we want to ingest from a Vercel deployment we need a
working blob driver.

- `pnpm add @vercel/blob`
- Implement `writeBatch` / `readBatch` / `cleanup` against `put` / `head` / `del`
- Key scheme: `scryfall/${runId}/batch-${index}.json`
- Set `BLOB_READ_WRITE_TOKEN` in the Vercel env
- Restore the `blob` case in `getBatchStorage()` to construct the new class
- Re-add coverage tests under `lib/staging/__tests__/blob.test.ts`

### Wire ingest auth to a real auth solution (was P0.2)

The current `INGEST_TOKEN` shared-secret check is intentionally crude: it
unblocks a deploy and stops drive-by abuse, but it does not give us per-user
attribution, rotation, or revocation. Once the app's auth layer exists, replace
the header check with whatever the rest of the API uses (session, JWT, Clerk
middleware, etc.) and rotate the token out of the env.

## Operational verification — needs a running environment

These cannot be exercised from CI today and require a real Postgres + network.
They should run as part of the next manual smoke test.

1. **Local ingest smoke test**
   ```sh
   pnpm db:up && pnpm db:migrate
   curl -X POST -H "x-maindeck-ingest-token: $INGEST_TOKEN" \
     http://localhost:3000/api/ingest
   ```
   Watch Prisma query logs. Expect non-zero `cardsInserted` / `printingsInserted`
   on the first run, and `cardsUnchanged` to dominate on the second run.

2. **Auth regression** — repeat the curl without the header; expect 401.

3. **Env-validation regression** — unset `DATABASE_URL` and start the dev
   server; expect a clear `env: DATABASE_URL is required but missing` error
   from the first request.

4. **Pool sizing** — during the local ingest run, confirm the pool stays at or
   below `DB_POOL_MAX`:
   ```sql
   SELECT count(*) FROM pg_stat_activity WHERE datname = 'maindeck_dev';
   ```

5. **Retry path** — temporarily point `fetchBulkManifest` at a URL that returns
   a single 500 (or use a local proxy) and verify `fetchWithRetry` recovers on
   the second attempt without failing the workflow step.

6. **Benchmark `$transaction` update path (was part of P1.2)** — run a full
   re-ingest with a forced version bump on every row (e.g. flip a hash input
   temporarily), measure batch wall-clock with and without the
   `prisma.$transaction([...])` wrapper. Expect the wrapped version to win on
   round-trip-bound workloads. If the win is not visible at 500-card batches,
   leave the wrapper as-is — correctness alone is reason enough.

## Intentionally NOT in scope (was P2.7)

These surfaced during the audit but were rejected with reason. Recorded here so
the next reviewer doesn't re-litigate them.

- **Repository pattern wrapping Prisma** — adds indirection without solving a
  real problem; Prisma is already a repository.
- **Parallelizing `upsertBatch` across batches in `ingest.ts`** — the workflow
  SDK's step semantics make sequential replay simpler to reason about;
  parallelism should wait until we measure it as the bottleneck.
- **Wrapping cards + printings in a single transaction** — the diff-based
  upsert already self-heals on re-run. A transaction spanning two `createMany`
  calls would hold a connection for seconds and hurt pool utilization more
  than it helps.
- **Replacing MD5 hash with incremental field-wise hashing** — premature;
  MD5-over-JSON is fast enough at 500 cards/batch.
- **Path-traversal hardening on `LocalFsStorage.dirFor`** — `runId` is
  generated by the workflow SDK, not user input. Not worth the validation
  layer.
- **Auto-generating `KNOWN_KEYWORDS`** — interesting but unclear ROI; leave the
  existing TODO.
