# Card and Deck reads use three styles, not a unified repository

Card and Deck data is read three ways: `'use cache'` query functions (`lib/card/queries.ts`, `lib/deck/queries.ts`) for RSC reads that benefit from cross-request caching and tag-based invalidation; direct Prisma calls in Server Actions, mutation snapshots (`lib/deck/mutation/snapshot.ts`), and auth gates (`lib/auth/deck-access.ts`) where the read must observe post-write state in the same request; and hand-rolled bulk reads in `lib/deck-io/card-resolver.ts` for fuzzy name resolution at import time.

A `CardRepo` / `DeckRepo` Module unifying these is rejected. Cache Components requires `'use cache'` to wrap functions directly — wrapping query methods on a class either loses cache semantics or duplicates per-method directives without composition. Mutation and auth reads must intentionally bypass cached reads to observe just-committed writes; routing them through the same Module would either cause correctness bugs or expose `findX` and `findXUncached` for every method, which is pure indirection. The shared concern that did warrant extraction — image-printing projection and pinned-Printing fallback — is concentrated in `lib/card/image.ts` (`IMAGE_PRINTING_FRAGMENT`, `resolveCardImage`) and reused by every consumer.

Revisit if (a) the same fan-out shape gets computed inconsistently across `'use cache'` and ad-hoc Prisma paths, or (b) a third Card/Deck projection emerges that gets duplicated across more than one query function. If a real n+1 emerges where the same key shape is fetched repeatedly within a request, reach for DataLoader at that point — the previous `lib/loaders.ts` scaffolding was deleted in favor of waiting for a real callsite.
